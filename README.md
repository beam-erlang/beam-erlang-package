# BEAM/Erlang package tool

This repository owns the Erlang implementation of `beam-pkg`, its source inventory,
compilation recipe, command-behavior tests and [package-format proposal](docs/package-format.md).
BEAM/Erlang supplies the native executable, relative `beam-pkg` alias and execution
host, and bundles a selected build of this tool in its installed distribution.

The experimental local builder produces Erlang/native archives and locks from
ordinary libraries and local source/archive execution dependencies. Native builds
use package-owned CMake recipes and the installed NIF SDK. The explicit workflow
is `beam build .`, `beam-pkg install .`, then `beam run --project .`. Installed
projects run on BEAM with standard I/O and declared native bindings. Tree remains
a stub. Whole OTP application recipes and compiler
plugins are deferred. See [commands](docs/commands.md) and
[package format](docs/package-format.md).

## Build and test independently

Use a matching installed BEAM/Erlang SDK, including its owned compiler tooling.
From this repository, select a matching Linux, macOS ARM64 or native Windows AMD64
MSVC EMU/JIT installation:

```sh
cmake -S . -B build/linux-emu \
  -DCMAKE_PREFIX_PATH="$PWD/../beam-erlang/install/linux-emu"
cmake --build build/linux-emu
ctest --test-dir build/linux-emu --output-on-failure
cmake --install build/linux-emu --prefix "$PWD/install/linux-emu"
```

CMake invokes the installed `beam compile` command and builds the explicit package
module inventory, `modules.txt` and generic `application.etf` descriptor under
`lib/beam/apps/beam-pkg`. Installation supplies that application and a launcher
bound to the selected installed `beam`. It supplies no VM. The payload is not
itself a `.bpkg.tar.gz` package.

The command, build, project, task and process-ownership suitesuse private copies of the
selected SDK with freshly compiled package policy. They cover immutable archives,
format-1 read compatibility, format-2 publication, native builds and actual NIF
execution through explicit modern composition, failure recovery, relocation,
project shells and native task handoff. On POSIX the task check verifies that native exec
retains the launched tool PID and process group. Windows checks preserve literal
arguments, exit status and interactive ConPTY input/output through native launchers. No suite modifies the input SDK.
Native Windows package compilation requires the x64 Visual Studio developer
environment, CMake and Ninja. Installed commands run from ordinary PowerShell.
Windows CMake resource exports use atomic selector files so symlink privileges
are not required. See the [Windows development record](../dev-documents/windows-development-baseline.md).
Python 3.11+ is required; native recipes additionally require their selected CMake
and C/C++ toolchain. Tests import no sibling runtime or playground sources.

## Distribution integration

The distribution selects this checkout with `BEAM_PACKAGE_SOURCE_DIR`, defaulting
to its sibling `beam-erlang-package` directory. Its CMake adapter calls the same
[compilation recipe](cmake/PackageTool.cmake) using the distribution's OTP-pinned
bootstrap. The standalone caller instead supplies the installed BEAM compiler.
Both callers receive the source-owned module inventory and generated bytecode.
The package-owned install recipe supplies the application descriptor and launcher;
the distribution supplies generic application hosting. No external Erlang,
automatic fetching or self-hosting is involved.

The descriptor and launcher bind the module inventory and SDK build identity.
The private entry receives the generic command context and returns `exit`, `run`
or `exec` actions. Project execution uses a fresh composition; native task exec
follows tool VM/system termination. This is a matching-build development contract,
not a public plugin interface. Rebuild both the bundled application and descriptor
when changing its modules. The two compiler paths are tested for behavior, not
byte-for-byte equality.

This repository is local-only, with no remote or published release. Hosted
distribution CI needs a selected source checkout before it can configure; publication
and CI source acquisition are deferred. Local validation must still run all required
checks. Never disable acceptance or use a floating download to hide missing sources.

## Ownership and scope

Framework manifests stay with their implementation sources; consumer manifests and
future workloads stay in the playground. The format is independently revisable;
it does not prescribe assembly of the separate OTP distribution described in the
[runtime strategy](../beam-erlang/docs/runtime-evolution-strategy.md). Existing
OTP package drafts preserve one complete application per package. Their build
recipes are not prerequisites for the distribution milestone. The modern BEAM
host's overlap with STDLIB-owned modules remains unresolved, so the draft
Erlangsters dependency graph is not executable yet.
Installed project shell accepts library roots without an entry. Source-only
`[scripts]` tasks use literal argv and native exec hosting after tool cleanup.
Native hosting, `beam run --project`, `beam shell --project` and `beam task`
dispatch belong to the distribution. Historical format
candidates remain workspace reference notes rather than competing specifications.

The extracted command policy retains its Apache-2.0 license. See [LICENSE.txt](LICENSE.txt).

The optional two-installation check exercises format-2 target closures and launch
pointers using two explicitly selected installed SDKs in one project:

```sh
python3 tests/targets.py --prefix "$EMU_SDK" --prefix "$JIT_SDK" --work "$SCRATCH/targets"
```

It preserves the first target's lock selection, executes each selected flavor,
and checks corruption isolation and recovery. It owns and cleans its scratch
project; the selected SDKs are read-only inputs. A compact result is written beside
`--work` as `<work-name>.json`; `--result` selects another external path.
